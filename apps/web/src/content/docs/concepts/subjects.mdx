A **subject** is what a conversation is about: an issue, a PR, a task, a repository, a
participant. The subject lives in the store that owns it, such as GitHub or Asana. cynapse
keeps the conversation about it, in a channel **keyed by the subject**. Everyone who works
on the subject meets in that one channel.

## Two kinds of channel

| | Work channel | Address channel |
| --- | --- | --- |
| Keyed by | A unit of work: an issue, a PR, a task, a mission | Something that receives messages: a participant, a repository, a project, a folder |
| Owner | None. It has members. | One participant, who triages it |
| Used for | The shared conversation about that piece of work | Direct messages: a question to a role, mail for an owner |
| Created with | `channel create` (the default kind) | `participant register`, or `channel create --kind address --owner <participant>` |

A work item's traffic goes on its work channel. Traffic addressed to a participant goes on
the participant's address channel. There are no separate mailboxes or DMs
([Messaging](/cynapse/concepts/messaging/)).

## Channels keyed by subject

A channel keyed by a subject gets its id from the subject's **native id** in its store:
GitHub's `node_id`, Asana's `gid`, Linear's UUID. Pass the store and the native id, and
cynapse builds the key `subject:<store>:<nativeId>` and the channel id `UUIDv5(key)`:

```console
$ cynapse --as builder channel create gh:acme/app/12 --store gh --native-id I_kwDOAbc012 \
    --type demo.issue --title "Login fails after reset"
created gh:acme/app/12  demo.issue  active  1 entries  Login fails after reset

$ cynapse channel resolve --store gh --native-id I_kwDOAbc012
gh:acme/app/12  demo.issue  active  1 entries  Login fails after reset
```

- **The key has no type.** Creating the channel again from the same subject returns it,
  whatever type or title the second caller gives. Two consumers that see the same issue
  differently still share one conversation.
- **The readable reference is a handle, not the key.** `gh:acme/app/12` changes when the
  issue moves to another repository; the native id doesn't change on a rename.
- **cynapse never calls the store.** The caller resolves the native id, for example with
  `gh issue view 12 --json id`, and passes it in. cynapse builds the key, so two callers
  that resolve the same id meet in the same channel. Never spell the key yourself.
- A store name is lowercase letters, digits, `.` and `-`, starting with a letter. A native
  id is kept exactly as the store returns it, with no whitespace.

## When the subject moves

Some moves give a subject a new native id. A GitHub issue transferred to another repository
does. Add the new id as an **alias key**, and the channel keeps its identity:

```bash
cynapse --as builder channel add-key gh:acme/app/12 --store gh --native-id I_kwDOXyz034
```

Both ids now resolve to the channel. Rename the handle with `channel rename` if the
readable reference changed too; the old handle stays as an alias.

## Address channels and owners

An address channel has one **owner**, the participant who triages it. Only the owner may
add or remove the `cynapse.handled` tag on its entries
([Messaging](/cynapse/concepts/messaging/#seen-versus-handled)).

- Registering a participant creates its address channel, keyed by the participant's id and
  owned by it ([Participants](/cynapse/concepts/participants/#registration)).
- A repository's address channel is keyed by its native id, such as
  `--store gh --native-id R_kgDOAbc`.
- Something with no native id, such as a folder, gets an address cynapse mints:
  `channel create --kind address --owner <participant>` without `--store`. Each call makes a
  new channel.
- `channel owner <channel> <participant>` changes the owner, logged as
  `cynapse.channel.owner-changed`.

The owner of an address channel is not a member of it. The channel doesn't appear in the
owner's `unread`; read it with `entry list <handle> --unread`
([Read state](/cynapse/concepts/read-state/#unread)).
